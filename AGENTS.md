# AGENTS.md

Rules for any coding agent working on Wisp. Read this before changing code, and read `README.md` for what the app does.

## Project

Wisp is a macOS notch app (shelf, live activities, coding-agent hub) written in Swift 6 with SwiftUI and AppKit. macOS 14 is the minimum; Liquid Glass needs macOS 26.

| Path | What lives there |
|---|---|
| `WispCore/` | Pure logic with no AppKit or SwiftUI. Static library, fully unit-tested. |
| `WispTests/` | XCTest suite for WispCore (`@testable import WispCore`). |
| `Wisp/` | The app: views, windows, and wrappers around system APIs, grouped by feature (`Notch`, `Shelf`, `Activities`, `Media`, `Services`, `Settings`, ...). |
| `WispAgent/` | `wisp-agent`, the hook command Claude Code and Codex call; it forwards hook events to Wisp. |
| `WispMediaBridge/` | Objective-C dylib hosted by `/usr/bin/perl` to read system-wide Now Playing. |
| `design/logo/` | Icon and menu glyph sources; `export.sh` renders them into the asset catalog. |
| `scripts/` | `release.sh` (DMG, Sparkle zip, signing, notarisation), `make-appcast.sh`, the git hook scripts and the Homebrew cask template. |
| `docs/REVIEW.md`, `PLAN.md` | Product review and the running plan with status. |

`Wisp.xcodeproj`, `Wisp/Resources/Info.plist` and `Wisp/Resources/Wisp.entitlements` are generated by XcodeGen. Change `project.yml`, never the generated files.

## Commands

```sh
make build    # xcodegen + Debug build: the separate "Wisp Dev" app (com.ayomideodewale.wisp.dev), own settings and permissions
make test     # WispCore unit tests
make lint     # swift-format lint --strict
make format   # swift-format in place
make run      # build Wisp Dev, quit any running Wisp (installed too), launch
make release  # universal Release DMG and Sparkle zip in build/release
make hooks    # install the lefthook git hooks
```

Test results: `xcrun xcresulttool get test-results summary --path "$(/bin/ls -td build/Logs/Test/*.xcresult | head -1)"`. In this shell `ls` is aliased to eza, so use `/bin/ls`.

## Before you say it's done

1. `make format`, then `make lint` passes.
2. `make build` has no warnings.
3. `make test` passes, with the count reported.
4. For UI or behaviour changes, `make run` and check it in the real app. If you couldn't verify something by hand, say so.
5. List anything skipped, stubbed, hardcoded or unverified at the end of your report.

## Code rules

- **Logic goes in WispCore, test first.** Anything that can be pure (parsing, sizing, rules, queues, formatting) is written in WispCore with tests before the app code that uses it. The app layer stays thin.
- **No type casts and no force unwraps.** No `as!`, `as?` used to make code compile, `try!`, `!` unwraps or implicitly unwrapped optionals. If a cast seems needed, fix the type model. swift-format enforces part of this.
- **Swift 6 strict concurrency.** UI and services are `@MainActor`; observable state uses `@Observable`. Don't silence concurrency errors with `nonisolated(unsafe)` or `@unchecked Sendable` without a comment explaining why it's safe.
- **Match what's there.** Mirror the nearest existing feature (for example, new stores follow `WeatherStore` in `Services/WidgetStores.swift`, floating panels follow `MiniPlayer`/`ClipboardPanel`). Check for an existing helper before writing one.
- **Logging:** `Logger(subsystem: "com.ayomideodewale.wisp", category: ...)`. Never log tokens, prompts, message bodies, file contents or other personal data.
- **Debug-only hooks** (distributed notifications such as `com.ayomideodewale.wisp.debug.toggleShelf`) stay inside `#if DEBUG`.
- **Settings** live in `Settings/Preferences.swift` and are backed by UserDefaults. New panes or options also get keywords in `WispCore/SettingsIndex.swift` so search finds them.
- **Animation:** the shell and its content move on one shared spring (`model.surfaceAnimation`). The shelf expands out of the notch and folds back into it on both axes; don't replace that with fades or width-only transitions. Respect Reduce Motion.
- **Accent:** Wisp violet (`Color.wispViolet`, `AccentColor` #7A6BFF) for selection, progress and active states.
- Comments explain why, not what. Keep them short and standalone.
- Format: 4 spaces, 120-column lines, ordered imports (`.swift-format`).

## Dependencies and system access

- The only third-party package is Sparkle (updates). Ask before adding any dependency or changing the stack.
- Ask before using a private Apple API or anything that needs permissions beyond Accessibility, Full Disk Access, Calendar, Notifications, Camera (Mirror) and Microphone status.
- Network calls are opt-in and minimal. Send only what the feature needs.
- **Feature lookups** are the one exception: they may be on by default only if all of these hold.
  1. They power a visible feature the user is using (lyrics and artwork while music plays), never in the background otherwise.
  2. They send the minimum data needed (track title, artist, album, length). Never files, clipboard contents, device identifiers or anything personal.
  3. They go to a public endpoint that needs no account or API key.
  4. Results are cached, so the same song isn't looked up twice.
  5. Each one has its own off switch in Settings.
  6. Each one is listed in the README's Privacy section: which service, what's sent and why.

  Anything that fails one of these stays opt-in. The only feature lookups today are LRCLIB (lyrics) and iTunes Search (artwork).
- Never edit `.env`, credentials, certificates or signing secrets.

## Writing

Applies to comments, docs, UI copy, commit messages and PR text.

- No em dashes. Use commas, semicolons, parentheses or separate sentences.
- Plain, concrete, human wording. No filler such as "seamless", "robust", "leverage", "delve" or "unlock".
- UI copy is short and sentence case ("Paste in Terminal", "Show lyrics").

## Git

- Never commit, push, tag, rebase, force-push or create or switch branches without explicit confirmation.
- **Use several commits.** One logical change per commit (feature, fix, docs, CI), staged by path or with `git add -p`, ordered so each commit builds. Never one bulk commit, even when a lot of work piled up.
- Conventional prefixes: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`, `perf:`.
- Branch names: `feat/short-description`, `fix/short-description`.
- **`main` is protected.** Never push to it. Push a branch and open a pull request at `https://github.com/Maestroharyor/wisp` using `.github/pull_request_template.md`. Pull requests are squash merged.
- **The PR title is a conventional commit.** It becomes the commit on `main`, and release-please reads it to pick the version (below 1.0: `fix` and `feat` bump the patch, `!` bumps the minor).
- **Releases come from the release PR.** release-please keeps a "chore(main): release x.y.z" PR open; merging it tags a draft release, and `release.yml` builds, uploads and publishes. Don't tag or bump `MARKETING_VERSION` by hand.
- **Required checks (`test` in `ci.yml`, `pr-title` in `pr-title.yml`) must never get path filters.** The release PR only touches `CHANGELOG.md` and `project.yml`; a skipped check would block it forever.
- Local hooks: `brew install lefthook && make hooks` (see `lefthook.yml`).

## Working style

- Plan first for new features, multi-file changes and non-trivial fixes, and get the plan approved. Keep long plans in `PLAN.md`.
- For bugs, state the suspected root cause and the fix before editing.
- Ask about real trade-offs; don't ask what the code or a sensible default already answers.
- After two failed attempts at the same fix, stop and explain what's going on.
- Keep `README.md`, `PLAN.md` and `docs/REVIEW.md` in step with what Wisp actually does.
